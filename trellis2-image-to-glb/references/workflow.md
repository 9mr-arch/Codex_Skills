# 이미지 업로드 → TRELLIS.2 설치·실행 → 텍스처 포함 GLB 자동 제작

## 사용 방법

이 MD 파일과 만들고 싶은 물체의 이미지를 파일·터미널·네트워크 도구를 사용할 수 있는 AI 에이전트 채팅에 함께 첨부하고, “이 지침대로 3D GLB로 만들어줘”라고 요청한다. 같은 대화에서 이 작업 모드가 유지되는 동안 새 이미지를 올리면 새 작업으로 처리한다. 사용자는 ComfyUI나 Python 설치 방법을 알 필요가 없다.

이 문서는 AI가 읽고 수행하는 실행 지침이다. MD 파일 자체가 프로그램처럼 실행되지는 않는다. 명령 실행이나 파일 접근 기능이 없는 채팅에서는 설치·추론을 수행했다고 말하지 말고, 실행 가능한 로컬 에이전트 환경이 필요함을 짧게 설명한다.

---

## 1. 역할과 완료 기준

당신은 이미지에서 텍스처가 포함된 3D GLB를 제작하는 작업 담당자다. 설치 설명이나 워크플로우 JSON을 전달하는 것만으로 끝내지 않는다. 환경 조사, 필요한 설치, 이미지 전처리, 형상 생성, 텍스처 생성, UV 베이크, 내보내기, 검증, 결과 전달까지 직접 수행한다.

사용자의 이미지와 명시적 요구가 모델의 추측보다 우선한다. 물체의 구성·부품 수·배치를 임의로 정리하거나 단순화하지 않는다. 만들어진 GLB는 실제로 다시 열어 확인하고, 여러 방향의 미리보기를 제공한다.

기본 결과물은 다음과 같다.

- `<object>_textured.glb`: 메시, UV, 재질, 텍스처가 포함된 독립 실행형 에셋.
- `<object>_preview.png`: 정면·사선·측면·후면을 확인할 수 있는 미리보기.
- `workflow_api.json` 및 가능하면 `workflow_ui.json`: 실행 재현 자료. ComfyUI를 거치지 않은 경우 재실행 스크립트와 설정으로 대체한다.
- `run_manifest.json`: 입력·출력 파일, 버전, 설정, 검증 결과, 추정한 부분의 기록.

기존 정상 설치를 재사용하고 누락된 구성만 준비한다. 일반적인 설치·다운로드·전처리·실행 여부를 사용자에게 반복해서 묻지 않는다. 실행 환경의 권한 요청은 정식 도구로 처리한다. 사용자의 확인이 필요한 것은 물체의 불명확한 구조, 계정 로그인·약관 동의, 새 비용·외부 전송, 시스템 차원의 변경 등 AI가 독자적으로 결정할 수 없는 사항이다.

## 2. 이미지 해석과 추가 자료 확보 — 생성 전 필수

첨부 이미지를 직접 열어 보고 다음을 판단한다. 파일명이나 사용자가 적은 품목명만으로 판단하지 않는다.

1. 제작 대상이 무엇인지, 한 물체인지 여러 물체의 조합인지.
2. 물체의 전체 윤곽이 보이는지, 잘리거나 다른 물체에 가려진 부분이 있는지.
3. 두께·깊이·다리·손잡이·지지대·개구부·내부 구조가 식별되는지.
4. 비대칭 구조나 접힌 부품, 투명·반사 재질 때문에 다른 형태로 오해할 가능성이 있는지.
5. 사용자가 일반적인 시각 에셋을 원하는지, 특정 제품의 구조·치수까지 맞추려는지.

결과를 `충분 / 구조 확인 필요 / 대상 지정 필요` 중 하나로 작업 기록에 남긴다. 모든 사물에 추가 사진을 요구할 필요는 없지만, 핵심 형태를 판단할 수 없다면 추가 자료 확보를 필수 단계로 취급한다.

### 구조 확인이 필요한 경우

형상 생성과 최종화를 보류하고, 무엇이 불명확한지 한 문장으로 설명한 뒤 필요한 각도의 이미지가 더 있는지 묻는다. 단순히 “사진을 더 주세요”라고 하지 않는다.

예시: “현재 사진에서는 책상 뒤쪽 지지대와 상판 깊이가 가려져 있어 형태가 다르게 만들어질 수 있습니다. 같은 책상의 측면이나 후면 사진도 있나요? 있으면 함께 올려주세요.”

- 사용자가 가진 동일 물체의 추가 사진, 이미 제공한 폴더·제품 링크·도면을 우선 수급한다. 사용자가 파일을 올릴 수 있도록 일반 채팅으로 요청한다.
- 제품명·모델 번호·공식 제품 링크가 제공됐다면 공개 제조사 자료에서 추가 각도를 찾아 동일 모델·색상·형태인지 비교한다. 비슷하게 생겼다는 이유로 다른 모델의 사진을 섞지 않는다. 출처와 대상 일치 근거를 기록한다.
- 사용자가 가진 이미지가 더 없고 대상 식별도 불가능하면 측면·후면 중 가장 필요한 촬영 각도를 구체적으로 안내한다. 모델 식별에 필요한 정보만 추가로 묻는다.
- 응답을 기다리는 동안 하드웨어 확인·설치·모델 준비 등 이미지 해석에 의존하지 않는 작업은 계속할 수 있다. 답변이 없다는 이유로 임의 추정을 승인받은 것으로 처리하지 않는다.
- AI로 만든 가상의 후면·측면이나 좌우 반전 복사본을 실제 관측 이미지처럼 사용하지 않는다.
- 추가 자료를 확보한 뒤 다시 구조를 평가한다. 여전히 모르는 핵심 부분이 있으면 그대로 고지한다. 사용자가 명시적으로 추정 제작을 허용했을 때만 추정 부분을 기록하고 진행한다.
- 정확한 치수나 기계적 결합 구조가 요구되는데 이를 확인할 자료가 없으면, 생성 모델의 결과를 실측 복원으로 포장하지 않는다.

### 추가 이미지를 받은 경우

동일 물체인지 먼저 확인하고, 각도를 판별한다. 기본 멀티뷰 구성은 정면·후면·좌측·우측의 최대 4개 입력이다. 임의의 사선 사진을 근거 없이 정확한 정면/후면 슬롯에 할당하지 않는다. 슬롯의 방향 정의는 설치된 구현을 확인한다. 각도가 부적합하면 추가 사진을 요청하거나 해당 사진은 구조 검토용으로만 사용한다.

한 장만으로 충분한 대상은 단일 이미지 경로로 진행한다. 한 장을 4개 슬롯에 반복해서 넣지 않는다. 2~3장만 있으면 실제로 존재하는 방향만 연결한다.

## 3. 실행 환경과 ComfyUI 설치 여부 자동 조사

사용자에게 설치 경로부터 묻지 말고 먼저 로컬에서 찾는다. 실행 중인 ComfyUI 프로세스와 명령행, 알려진 설치 위치, 앱 설정·로그, 작업 폴더를 순서대로 조사한다. 사용자 디스크 전체를 무차별 검색하지 않는다.

확인하여 작업 기록에 저장할 항목:

- OS·아키텍처, GPU 모델·VRAM·드라이버, RAM, 모델 저장 볼륨의 남은 공간.
- ComfyUI Desktop / Portable / 수동 설치 여부, 실제 코어 경로와 사용자 데이터 경로.
- 실제 Python 실행 파일, Python·PyTorch·CUDA 런타임 버전, `torch.cuda.is_available()`와 간단한 GPU 연산 결과.
- `custom_nodes`, `models`, `input`, `output`, 사용자 워크플로우의 실제 위치와 추가 모델 경로 설정.
- 실행 중인 서버 주소·포트·현재 큐, TRELLIS2 노드 등록 여부와 커스텀 수정 사항.

`python`이 PATH에 없다는 이유로 새 Python부터 설치하지 않는다. Desktop의 가상환경과 Portable의 내장 Python을 구분하고, 해당 ComfyUI가 쓰는 정확한 실행 파일로 검사·설치한다. 가상환경 실행이 실패하면 `pyvenv.cfg`의 기반 Python 경로와 접근 권한부터 확인한다.

ComfyUI가 다른 GPU에서 실행된다는 사실이 TRELLIS.2 CUDA 확장 호환성을 보장하지 않는다. 공식 TRELLIS.2의 문서상 기준은 Linux와 24GB 이상 NVIDIA GPU이며, Windows 및 저VRAM 경로는 선택한 래퍼·바이너리 조합을 따로 검증해야 한다. 실행 시점의 [공식 요구사항](https://github.com/microsoft/TRELLIS.2#-installation)을 재확인한다.

호환 GPU가 없으면 성공할 것처럼 대용량 설치를 계속하지 않는다. 이미 사용 권한이 있는 적합한 GPU 환경을 확인한다. 새 클라우드 비용이나 이미지 외부 업로드가 필요하면 대상·비용을 확인받는다. CPU 전용 또는 Apple/AMD 환경에서 ComfyUI가 켜지는 것만으로 TRELLIS2 실행 가능 판정을 내리지 않는다.

## 4. 설치가 없는 사용자도 AI가 직접 준비

### 설치 경로 선택

1. 기존 ComfyUI와 TRELLIS2가 정상 동작하면 그대로 활용한다.
2. 기존 ComfyUI에 필요한 노드·의존성이 없으면 현재 환경과 충돌 여부를 먼저 확인한다.
3. 핵심 PyTorch 교체 등으로 기존 작업을 깨뜨릴 가능성이 크면, 작업 전용 디렉터리에 별도 ComfyUI·가상환경을 설치한다. 정상 환경을 무조건 업그레이드하거나 삭제하지 않는다.
4. ComfyUI가 없으면 공식 설치 자료에서 운영체제에 맞는 배포를 선택하고 직접 다운로드·설치한다. 가능하면 사용자 권한으로 설치 가능한 격리 환경을 사용한다. 사용자가 웹에서 설치 파일을 찾아오거나 터미널에 명령을 복사하게 하지 않는다.
5. Linux 등에서 공식 TRELLIS.2 직접 실행 경로가 더 적합한 경우, ComfyUI 확인 결과와 경로 선택 이유를 짧게 설명하고 검증된 공식 파이프라인으로 제작할 수 있다. 최종 결과물 기준은 동일하다.

### 호환성 결정 후 설치

필요한 구성은 공식 또는 선택한 래퍼의 관리자가 제공한 저장소·릴리스에서 가져온다. 아래를 참고하되 패키지 버전과 wheel 파일명을 문서에서 복사해 고정하지 말고 현재 제공 목록과 로컬 환경을 대조한다.

- ComfyUI 및 [ComfyUI-Trellis2 래퍼](https://github.com/visualbruno/ComfyUI-Trellis2).
- TRELLIS.2 모델·설정 파일과 파이프라인이 요구하는 이미지 인코더 가중치.
- 형상·텍스처 처리용 CUDA 확장: CuMesh, O-Voxel, FlexGEMM, nvdiffrast, nvdiffrec 계열 등 실제 실행 경로에서 요구하는 패키지.
- 이미지·메시 처리 의존성, 자동 배경 제거 패키지와 해당 모델, 필요한 ONNX 실행 환경.
- 선택한 attention backend와 sparse backend의 별도 의존성.

Windows wheel은 OS·CPU 아키텍처·Python ABI·PyTorch·CUDA 호환 조건을 맞춰 선택한다. Python `cp311` 바이너리를 `cp312`에 억지로 설치하지 않는다. 소스 빌드가 필요하면 해당 저장소의 요구 툴체인부터 확인한다. GPU 드라이버나 시스템 재부팅이 필요한 변경은 별도로 설명한다.

설치 전후 패키지 목록과 저장소 커밋을 기록한다. 기존 커스텀 수정은 보존한다. 각 핵심 모듈의 import뿐 아니라 필요한 함수가 실제 호출 가능한지, 작은 GPU 연산이 실행되는지도 확인한다. FlashAttention 함수가 `None`인 상태는 설치 성공이 아니다. dense attention과 sparse attention의 지원 backend를 각각 확인하여 테스트된 대체 경로를 선택한다.

### 모델 다운로드와 계정 접근

선택한 파이프라인의 설정을 읽어 실제 필요한 파일을 열거하고 기존 캐시를 재사용한다. 다운로드 용량·여유 공간을 확인하고 재개 가능한 방식으로 받는다. 학습 데이터나 사용하지 않는 다른 모델까지 전부 다운로드하지 않는다.

기본 모델은 `microsoft/TRELLIS.2-4B`이며, 래퍼가 요구하는 인코더는 설치본을 기준으로 확인한다. DINOv3 등 접근 승인 모델이 필요하면 기존 로그인과 접근 권한을 먼저 검사한다. 접근이 없을 때만 사용자가 직접 해야 하는 로그인·동의를 요청한다. 승인 절차를 우회하거나 토큰을 채팅·로그에 노출하지 않는다. 모델 다운로드 후 누락·불완전 파일과 실제 로딩을 검사한다.

설치를 완료한 경우 서버를 로컬 주소에 띄우고 로그와 API 응답으로 기동을 확인한다. 다른 작업의 큐를 지우거나 실행 중인 서버를 임의로 종료하지 않는다. 재시작이 기존 작업을 방해한다면 유휴 시점 또는 별도 인스턴스를 사용한다. Windows 백그라운드 기동은 숨김 창으로 처리한다.

## 5. 원본 이미지부터 자동 전처리

사용자에게 누끼·알파·크롭·해상도 변환을 수작업으로 요구하지 않는다.

1. 원본을 보존하고 EXIF 회전과 색상 모드를 정규화한 작업 사본을 만든다.
2. 유효한 알파가 있으면 이를 활용한다. RGB이거나 알파가 전부 불투명하면 배경 제거 모델을 실제 실행한다.
3. 마스크를 검사한다. 빈 마스크, 물체 잘림, 다리·손잡이·얇은 종이 손실, 그림자의 물체 오인 여부를 확인한다. 실패하면 분리 설정이나 지원되는 다른 분리기를 조정한다.
4. RGBA를 요구하는 전처리에는 올바른 4채널 이미지를 넘긴다. 알파 없는 RGB에 바로 네 번째 채널을 읽는 오류를 방지한다. 물체가 하나도 검출되지 않은 마스크로 bounding box 계산을 진행하지 않는다.
5. 비율을 유지해 중심과 여백을 정렬한다. 배경 제거 결과와 실제 모델 입력을 미리보기로 저장하고 AI가 직접 본다.
6. 여러 각도는 주요 구조와 상대 비율이 유지되도록 정렬한다. 각 사진의 폭을 무조건 같게 만들어 깊이 정보를 왜곡하지 않는다. 구현에 따라 입력 배경색·알파 처리 방식은 다를 수 있으므로 실제 전처리 코드를 확인한다.

## 6. 형상과 텍스처가 모두 연결된 실행 그래프 작성

현재 등록된 `/object_info`와 노드 구현을 기준으로 API 실행 그래프를 구성한다. 설치본에 포함된 예제는 출발점으로 사용하되, 예제나 이전에 만들어진 JSON이라는 이유만으로 정상이라고 가정하지 않는다. 노드 이름·입출력 타입·필수 설정은 버전에 따라 달라질 수 있다.

단일 이미지의 기본 순서:

`이미지 로드 → 배경 제거·크롭 → TRELLIS2 모델·이미지 조건 → 형상 생성 → 텍스처 생성 → 디코드 → 필요한 메시 정리 → UV·텍스처 베이크 → GLB 저장`

최대 4장 멀티뷰의 기본 순서:

`각 이미지 전처리 → 방향별 이미지 조건 → 멀티뷰 형상 생성 → 같은 방향별 조건을 사용한 멀티뷰 텍스처 생성 → 디코드 → UV·텍스처 베이크 → GLB 저장`

멀티뷰는 선택한 래퍼의 구현 기능으로 취급한다. 단순 이미지 배치, 방향별 멀티뷰, 공식 단일 이미지 파이프라인을 동일한 것으로 간주하지 않는다.

그래프 검증 규칙:

- 단일 이미지에는 한 입력만 사용한다. 선택적 입력은 사용하지 않으면 API 그래프에서 제외한다. 비어 있는 로더나 입력이 끊긴 전처리 노드를 실행 대상으로 남기지 않는다.
- UI workflow JSON과 API prompt JSON을 구분한다. `widgets_values`의 위치만 추측해 API 입력으로 바꾸지 말고 실제 스키마와 대조한다.
- 링크 ID 존재 여부만 검사하지 않는다. 모든 링크의 출발 노드·출력 슬롯·도착 노드·입력 슬롯·타입과 양쪽 링크 기록이 일치해야 한다. 서로 다른 연결에 같은 ID를 재사용하지 않는다. 순환·고립·중복 노드도 검사한다.
- 형상 latent와 텍스처 latent가 디코더에 모두 들어가야 한다. 베이크 노드가 요구하면 디코더의 BVH도 연결한다.
- 이미지 조건, 방향 목록, 형상 해상도와 텍스처 생성 해상도가 서로 호환되는지 확인한다. 모델이 지원하지 않는 해상도를 강제하지 않는다.
- 최종 GLB exporter가 텍스처·재질을 가진 메시를 받는지 확인한다. 무재질 메시 변환 노드로 잘못 우회하지 않는다.
- 출력은 UV와 이미지 텍스처를 포함해야 한다. 버텍스 컬러만 저장한 모델을 텍스처 포함 결과로 전달하지 않는다.

형상 해상도와 텍스처 이미지 해상도는 별개다. 최초 제안값은 가능한 환경에서 형상 1024 계열·텍스처 2048이며, 설치본 기본값과 실제 메모리 사용량을 보고 조정한다. seed를 기록한다. 메모리가 부족하면 단계별 모델 해제·tiled decode·지원되는 저VRAM 설정을 먼저 검토하고, 필요할 때 해상도를 낮춘 사실을 알린다. 품질 확인 전에 무조건 최고 설정으로 올리지 않는다.

메시 정리에서는 의도한 구멍·책상 아래 공간·손잡이 틈을 막지 않는다. 작은 부품을 노이즈로 일괄 삭제하지 않는다. 파트 삭제·hole fill·과도한 단순화는 원본과 비교하며 적용한다.

## 7. AI가 직접 실행하고 오류를 해결

ComfyUI API를 사용할 때는 현재 서버가 제공하는 [HTTP·WebSocket 경로](https://docs.comfy.org/development/comfyui-server/comms_routes)를 확인한다.

1. 서버 상태와 노드 등록·모델 파일을 검사한다.
2. 입력을 업로드하거나 실제 input 폴더에 복사하고 서버에서 인식하는 파일명을 사용한다.
3. 검증한 API 그래프를 `/prompt`에 제출하고 반환된 `prompt_id`를 기록한다. 요청 타임아웃 때는 큐·이력을 먼저 확인하여 중복 제출을 막는다.
4. WebSocket 또는 해당 작업의 `/history/{prompt_id}`로 진행·오류를 추적한다. 다른 사용자 작업의 이력과 결과를 혼동하지 않는다.
5. 오류가 있으면 실패한 노드와 로그를 읽고 원인을 고쳐 해당 단계부터 재시도한다. 잘못된 wheel, 모델 누락, 잘못된 입력 링크, attention 함수 오류, VRAM 부족, UV 오류를 같은 문제처럼 처리하지 않는다.
6. 동일 실패를 설정 변경 없이 무한 반복하지 않는다. 사용할 수 있는 로컬 대안을 검사한 뒤에도 해결할 수 없으면 구체적인 차단 원인과 이미 시도한 조치를 알린다.
7. 결과 경로는 실행 이력·노드 반환값을 통해 찾는다. 파일이 생성됐는지 확인하고 검증 단계로 이동한다.

실행 중에는 설치·모델 준비·생성·검증처럼 사용자가 이해할 수 있는 짧은 진행 상황을 알린다. 실제 실행 없이 “백그라운드에서 진행 중”이라고 말하거나, 설치만 완료한 상태에서 제작 완료를 선언하지 않는다.

## 8. GLB 검증과 품질 보정

완료 판정은 아래 검사를 통과한 뒤 내린다.

- 파일을 GLB로 재로드할 수 있고 유효한 정점·면·유한한 좌표·정상적인 크기를 가진다.
- UV, PBR 재질, base color 텍스처가 실제로 참조되며, 생성된 metallic/roughness 등도 올바른 채널로 연결된다.
- 텍스처는 GLB 내부에 포함돼 있다. 임시 폴더나 외부 PNG 경로가 있어야만 보이는 파일은 수정한다. 호환성을 고려해 PNG/JPEG 등 대상 뷰어가 지원하는 포맷을 우선한다.
- 앞·뒤·좌우·사선에서 렌더하여 검은 재질, 텍스처 누락, UV 이음새, 뒤집힌 면, 떠 있는 부품, 잘못된 방향, 찌그러짐을 직접 확인한다.
- 참조 이미지와 비교해 실루엣·깊이·부품 수·배치가 맞는지 확인한다. 뒷면은 관측 자료가 있을 때만 일치 판정을 내리고, 미관측 영역은 추정이라고 기록한다.
- 유리·얇은 재료는 alpha와 양면 설정이 실제 렌더에 반영되는지 확인한다. 모든 재질에 투명을 일괄 적용하지 않는다.
- 사용자가 치수를 제공하지 않았다면 실제 단위·크기를 정확히 복원했다고 말하지 않는다.

문제가 전처리·샘플링·베이크 설정에서 비롯되면 직접 보정하고 필요한 단계만 다시 실행한다. 핵심 구조 오해가 발견되면 해상도를 높이는 것으로 덮지 말고 2절의 추가 자료 확보 단계로 돌아간다. 해결되지 않은 결과는 검토용 초안으로 표시하고 완성품이라고 전달하지 않는다.

## 9. 저장·재사용·최종 응답

작업마다 전용 폴더를 만들고 원본·전처리·출력·로그를 분리한다. 기존 결과를 덮어쓰지 않고 버전을 붙인다. 다음 이미지에서는 확인된 설치와 모델 캐시를 재사용한다.

`run_manifest.json`에는 작업 상태(`waiting_for_reference`, `preparing`, `generating`, `validating`, `complete`, `blocked`), 환경·저장소 버전, Python 경로, 모델 출처, 입력 해시·각도·출처, seed·해상도·설정, prompt ID, 출력 경로, 검증 결과와 추정 부분을 남긴다. 중단 후 재개할 때 이 기록과 실제 파일을 대조한다. 비밀번호·토큰은 기록하지 않는다.

최종 응답은 간단하게 작성한다.

1. 실제 생성한 텍스처 포함 GLB 링크.
2. 여러 방향의 미리보기 이미지.
3. 사용한 이미지 수, 텍스처 해상도, 핵심 검증 결과.
4. 추정한 뒷면 등 결과에 중요한 한계가 있으면 한 문장.

설치 설명을 최종 결과 대신 전달하지 않는다. 생성이 차단되었다면 완료를 주장하지 말고, 필요한 자료나 사용자의 불가피한 조치만 구체적으로 요청한다.
